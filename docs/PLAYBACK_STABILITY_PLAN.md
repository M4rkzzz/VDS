# VDS 两种播放器轻量稳帧改造与验收

日期：2026-10-07。原计划的时间戳与背压、呈现调度、音画时钟三部分已落地。改造保留 FFmpeg、WebCodecs、GDI、Canvas、waveOut 和 Web Audio，将短乱序、解码压力、呈现期限和源切换收进现有播放边界；保持纯 P2P，禁止 TURN。本轮没有增加通用调度框架或更换渲染后端。

两端已经具备按 PTS 呈现和音频输出时钟，但长时真实音画与性能收益仍以验收结果为准。当前产品和连接状态见 [项目现状报告](PROJECT_STATUS.md)，问题记录见 [代码审计问题清单](CODE_AUDIT_FINDINGS.md)。

## 时间戳和媒体源代次

原生房主共用一个单调时钟原点，同一编码内容向不同 peer 分发时保留相同 PTS 和源序号。WGC 使用捕获帧的 QPC 时间；FFmpeg Annex B 输出没有携带捕获 PTS 的通道，按首次输出及帧率估计，明显停顿后重新锚定。WASAPI 当前入口也以回调时刻、块时长和采样游标估计源采样时间。这些估计不能替代采集设备时间戳的实测音画精度。

DataChannel 的 64 位微秒 `timestampUs` 直接进入原生解码、音频播放和编码接力，避免绕经 32 位 RTP。有效的零时间戳被保留。OBS 使用容器公共时基并加上房主公共时钟偏移；同一房主会话内 OBS 重连更换源代次，PTS 可以连续，不要求归零。缺失 PTS 使用相应回退，旧 RTP 入口单独处理回绕。自带编码器关闭 B 帧，OBS 输入继续支持 B 帧：编码包按序号送入解码器，解码输出按 PTS 呈现，不用非单调的编码 PTS 重排参考链。

媒体 v1 头部新增可选的 `sourceEpoch`，旧格式继续兼容。房主每次源会话创建新代次，OBS 每次重新连接更换代次。原生和 Web 接力为每个下游媒体绑定生成短的独立输出代次，上游换代或重新绑定时更新；同一绑定内音视频共用代次，PTS 和内容序号继续保留。这样 A → B → A 切源时，第二次 A 使用新代次，旧 A 的迟到帧不能恢复旧播放，也无需为换画面重新建立下游 ICE。

接收端在换代时清理解码器、重排、待呈现帧和音频时钟，Web 保留已经由用户手势解锁的 AudioContext。接受新代次后拒绝退役代次和缺少代次的旧帧降级。精确记录本接收会话的退役代次，结束后释放；切源次数和运行时长不封顶。2048 次原生及 1024 次 Web 换源回归验证新源持续接受、最旧源仍拒绝，避免人为次数上限中断正常运行。

## 原生播放结构

| 环节 | 已实施行为 |
| --- | --- |
| 编码输入 | 按源帧率及实际音频时钟落后量调整压缩帧容量，容纳约 250 ms 的正常聚包，未获帧率时允许常见 60 fps 突发。按发送序号处理短乱序，缺口等待约 20 ms；配置与同序号 IDR 可组成 bootstrap。已消费的新配置更新恢复缓存，同序号迟到配置先于下一帧消费。 |
| 参考链恢复 | 超时缺口或过载使参考链失效时清理并等待配置和完整随机访问帧，关键帧请求合并并以 500 ms 间隔重试。正常迟到优先丢已解码画面，避免任意裁剪压缩参考帧。 |
| 解码与呈现 | 每个活动播放器一个解码和调度 worker，条件变量等待输入或最近期限。待呈现队列满时先等待显示腾位，把短时积压留在有界压缩队列，避免未来帧被连续覆盖而饿死。窗口线程负责 GDI 绘制，最多一个待处理呈现通知；不在窗口线程解码。 |
| 画面资源 | 待呈现最多 2 帧，BGRA 估算预算 32 MiB；4K 时收缩为 1 帧。缓冲移交所有权并复用，GDI backbuffer 仅在尺寸变化时重建。迟到帧尽量在硬件回读和颜色转换前丢弃。 |
| 显示时钟 | 有效且匹配媒体源的 waveOut 输出时钟驱动视频，用户音频延迟作为明确偏移保留；没有有效音频时回退单调时钟。目标缓冲在 20–60 ms 内调整；无音频时连续四个解码输出超过 40 ms 迟到阈值会重新锚定，避免固定网络延迟变化造成永久丢帧。 |
| 生命周期 | 停止先通知 worker，再等待结束并释放解码器、画面池和 GDI 资源；旧 source、旧 receiver 和关闭后的回调无法恢复已停止播放。 |

32 MiB 是待呈现画面的软目标，较大的单帧仍允许一个呈现槽位，不额外限制已支持的分辨率。解码器 DPB、显示中的画面、可复用缓冲和 GDI backbuffer 另计，不能当作播放器总内存上限。单次慢解码仍可能错过期限；诊断分别记录解码输出、实际绘制、迟到、丢弃、参考链复位和当前队列。

纯 DataChannel 的关键帧请求现已实际发送和解析，并可沿接力链回到源端；会话、版本、连接代次及 500 ms 合并保护会拒绝旧请求和重复风暴。桌面房主收到请求后通过现有单线程 RPC owner 重开 FFmpeg/WGC，不再等 5 秒界面轮询；新编码器尚未完成首个 bootstrap 时不重复重启，采集时钟和内容序号仍保留。它不是编码器原地强制 IDR。独立使用 native 时，调用方须消费 `host-video-refresh-requested` 事件并调用 `getStats`；OBS 的外部编码器仍等待周期 IDR。

## Web 播放结构

`EncodedMediaPlaybackSession` 统一拥有帧重组、源代次、序号重排和两个播放器。`main.ts` 保留房间、信令、上游恢复与编码接力；本地播放失败或丢显示帧不会阻断已校验编码帧向下游转发。

视频移除逐帧 20 ms 延时任务，改为小型解码输出队列和单个 `requestAnimationFrame` 呈现循环。每次回调最多画一帧，已被更新的到期画面替代的旧帧立即关闭；队列为空停止循环。待呈现通常最多 2 帧；输入 PTS 回退确证 B 帧重排时允许最多 3 帧，以容纳 codec 突发输出。32 MiB 是尺寸估算软目标，4K UHD 和更大单帧使用 1 个槽位，不额外禁用解码器已支持的尺寸。Canvas 和 GDI 的提交计数都不代表屏幕物理呈现或 Vsync。

解码背压同时查看 `decodeQueueSize`、待提交输入和提交后尚未输出的工作。待呈现及在途输出占用预约容量时暂停下一次提交，由 rAF 腾位唤醒；B 帧自身需要保留的输出按已经观察到的重排深度计入预约。视频压缩输入容量按源帧率、250 ms 聚包窗口及实际音频时钟落后量调整，12 是基础容量，不是帧率上限；接力 manifest 的 `fps` 与原生 `frameRate` 均传入策略，未声明时用已有的输出帧间隔估计。已确认 codec 正常保留的 B 帧在主动等待音频呈现期限期间不消耗停滞额度；恢复提交后，真正 500 ms 无输出仍恢复，原始提交年龄与有效停滞时间分别诊断。网络抖动采样取编码输入的到达时间，不把解码器集中输出误判为网络抖动。`decodeQueueSize` 不能覆盖 codec 全部内部工作。[WebCodecs 规范](https://www.w3.org/TR/webcodecs/#videodecoder-interface)

音频按源 PTS 预约 AudioBufferSource，跟踪预约音源；结束后移除，重锚、换代和关闭时停止并断开旧音源。复用已有 24 包压缩队列，预约余量不足时先等待再提交解码，避免常见 235 ms、11 AAC 包的 OBS 突发被 PCM/音源上限切掉尾部。新到突发的首包已过期时有界重锚；codec 在途最多 12 个工作，最老实际提交超过 500 ms 后恢复，不让部分慢输出不断续命。同房间更换上游保留已解锁的 AudioContext，实际离房关闭。视频优先参照有效的音频输出位置，否则用单调时钟；目标缓冲维持 20–60 ms。实时计数仍逐次累计，JSON、DOM 和丢帧日志最多刷新 4 Hz。隐藏页面的 rAF 可能暂停，帧持有和解码压力仍有上限。

实际 SRT 重连会短时追赶近一秒的媒体。已运行且完成配置的音频队列确实满时，若收到同 codec 的更近 PTS/序号，取消旧待提交积压并接受新包重新锚定，保留已解锁的 AudioContext。该过程会舍弃部分恢复期声音，避免持续播放过时内容；不是完整无损播放承诺。正常 235 ms 聚包不触发此恢复，慢能力探测期间仍遵循既有入口背压。

## 音频输出与延迟边界

原生 PCM 块保留 PTS 和采样长度，`waveOutGetPosition` 的实际返回格式经过检查，设备采样位置映射回源 PTS。设备 reset、位置失效、源切换或丢块后同步更新映射。worker 使用输出事件唤醒，空闲时阻塞；有在途声音时有限采样设备位置，避免持续空轮询。

默认设备在途音频最多 60 ms，软件队列与设备共同计入默认 120 ms 总积压目标，用户音频延迟计入同一预算。合法的不可分音频单元超过目标时，临时容纳完整单元及最多 60 ms 的已有尾部，消费后恢复默认目标。例如 8 kHz AAC 的 128 ms 单元不会因额度被截断。原生复用既有 worker，压缩输入以 24 包、1 MiB 为目标；合法较大单 blob 可单独容纳，通过游标逐个 ADTS 或 20 ms PCMU 段消费，不展开成大量任务。RTC 回调先独立接力，再轻量提交本地播放。500 ms 恢复只用于已经到期且设备确无播放进展的任务，仍在未来的尾部继续播放。

真实 11 AAC 突发原先立即解码会丢 6/11 包、约 128 ms；改造后连续 10 轮共 110 包全部播放，PCM 和编码丢弃为零，PCM 峰值 5120 样本帧，低于常规 5760 目标。1414 个原生音频断言覆盖低采样率 AAC、多 ADTS、200 ms 与 1250 ms PCMU、设备停滞及关闭恢复，全部通过。Web 同样容纳合法大音频单元；AAC 解码器的连续样本时钟用于校验，预约播放使用相应输入的源 PTS，源时间跳步后不持续失配。

迟到或重复的编码音频被丢弃，PCM 按时间处理；本轮没有实现完整的编码音频乱序缓冲。既有 libswresample 用于将非 48 kHz 双声道音频转换到输出格式，正常 48 kHz 双声道直接走原路径；该格式转换不是用于长期漂移修正的变速系统。20–60 ms 是调度目标，不是端到端延迟承诺；源封装聚包、SRT/WebRTC 传输和设备延迟另计。

Web 优先使用 `getOutputTimestamp()` 估计音频输出位置；原生使用 waveOut 实际采样位置。两端都有无有效音频时钟的回退路径。用户 Web 音量为零时直接使用已有视频单调时钟回退，避免虚拟静音音频设备拖慢画面；恢复音量后继续使用当前输出位置，保留 AudioContext 和解码器。这些输出估计、静音播放计数和隐藏窗口绘制均不能证明真实音画偏差达到 50 ms。

验收曾发现测试图内全零音量约 30 秒后，AudioContext 时钟由约 1 倍速降到约 0.65 倍速；与 Chromium 的 [30 秒静音切换实现](https://chromium.googlesource.com/chromium/src/+/HEAD/content/renderer/media/renderer_webaudiodevice_impl.cc)及 [SilentSinkSuspender](https://chromium.googlesource.com/chromium/src/+/HEAD/media/base/silent_sink_suspender.h)相符。常规吞吐测试现保持图内正常音量，在窗口层静音，另测用户音量为零的回退。窗口层静音仍不等于物理设备发声，报告不以它证明真实音画精度。

两种 profile 都覆盖初次播放、持续播放、离房重进、刷新重进、Web 二跳、保持 peer 的两次 OBS 源重启，以及 relay 离线后的上游恢复。重启追赶期间会有意取消旧音频积压：30 fps 两次各 24 包，60 fps 分别 48 和 24 包；恢复后新代次继续产生视频与音频，原 peer 和 transport 代次保留，不能把稳定段零音频丢弃写成所有阶段无损。

每秒采样显示，30/60 fps 待呈现最多分别 3/2 帧，输入等待分别 9/17 包，codec 排队均为 0；ready BGRA 估算分别约 23.9/15.9 MiB。采样窗口中的调度迟到 P95 最大值分别为 13.035/14.518 ms（窗口为最近 128 次呈现）；60 fps 曾出现 42.866 ms 的单次迟到。它们是采样与软件提交数据，不能代表全部瞬间峰值。

Electron 各进程 CPU 总和采样中位数分别约 1.30%/1.68%，工作集总和中位数约 1037/1093 MiB；不包含 FFmpeg 源或原生 Agent，工作集还可能重复计入共享页面。改造前的隐藏窗口即时绘制与当前 offscreen 环境不同，因此这些数据用于复现，不用于宣称 CPU 或总内存降低。完整原始报告在 `tmp/playback-final-1080p30-b2.json` 和 `tmp/playback-final-1080p60.json`。

后续性能验收仍按同一机器、同一源和同一显示环境对照 1080p30、1080p60，各持续 10 分钟；区分到达、解码输出和绘制提交，稳定场景调度迟到 P95 以不超过一帧周期为目标。30 分钟实际声音输出的同步图案测试，以音画偏差 P95 不超过 50 ms 为初始目标；连续 100 次完整开始和停止用于观察资源是否增长。这三项是验收目标，尚不能由短时静音测试替代。

本轮已验证普通聚包的参考链保留、短时近源帧率和两次同连接换源恢复。D3D11 零拷贝、Web Worker、AudioWorklet、变速和插帧未纳入本轮。持续带宽不足或传输重传仍需要根据连接积压证据处理，接收调度无法消除所有停顿。
